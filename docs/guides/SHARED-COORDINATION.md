# Shared admission and credential coordination

The default account semaphore remains local. Opt-in shared admission uses a dedicated native SQLite/WAL database on a shared local POSIX volume. Both overlapping generations must support `omni-coordination/v1`. The previous deployed build cannot safely overlap merely because a new candidate supports it.

Configure `OMNI_SHARED_ADMISSION=true` and `OMNI_COORDINATION_DB=/app/data/coordination.sqlite` in each compatible process. Existing dashboard global/provider/account limits remain the ceilings; no provider subscription limit is invented. Waiting reservations hold no partial capacity. Overlapping resources follow FIFO across processes; independent resources can progress. Durable cooldowns cannot be shortened by another process. Lease loss aborts upstream dispatch; ownership is fenced by process, lease ID and generation.

Quota identities remain connection-specific unless `providerSpecificData.quotaGroup` explicitly declares a shared budget, or `quotaIdentityVerified=true` and `quotaAccountId` identify an authenticated quota principal. `quotaRealm`, `quotaTenantId`, `quotaProjectId`, and `quotaPartition` distinguish independently metered budgets. Emails and display names never merge quotas. Account admission does not replace dashboard routing priorities, forced-account selection or valid affinity.

Shared account admission now uses the existing measured admission-window algorithm by default. With no account cap configured, it starts at four concurrent generation attempts and has a local policy ceiling of 32; these numbers are conservative scheduler policy, not a measured provider subscription entitlement. An explicit positive `maxConcurrent` replaces the ceiling and starts at `min(4, maxConcurrent)`. Global and provider ceilings are still independent fixed gates. Explicit account `maxConcurrent=0` retains the unlimited bypass. Outside shared mode, the existing local semaphore behavior is unchanged.

`providerSpecificData.quotaAdaptiveAdmission=false` opts out of measured adaptation: an explicit positive cap stays fixed, and an absent cap uses the cautious fixed starting limit of four. The `true` value remains accepted. All feedback and admission use the same selected canonical quota identity; account/model routing, explicit pins and independently declared quota realms are unchanged.

Only an explicit concurrency-overload classification reduces current admission; generic 429 quota exhaustion, authentication errors and generic timeouts do not. A verified concurrency overload halves the current limit once per 30-second measured window, down to at least one. Existing in-flight requests keep their leases and are not cancelled merely because the limit decreased. Healthy completed work with at least 70% measured utilization can increase admission by one per window up to the applicable ceiling. Idle recovery only returns toward the starting limit, so an idle unknown account does not grow toward 32 without evidence. This feedback is consumed by actual shared acquisition across processes; it is not only dashboard telemetry.

Generation retries share a request-owned attempt/deadline budget across model/account/host and fresh/native transport attempts. Defaults are 12 generation sends and a 900,000 ms retry-admission deadline, configurable with `OMNI_LOGICAL_RETRY_MAX_ATTEMPTS` and `OMNI_LOGICAL_RETRY_DEADLINE_MS`. The deadline does not cut an already-running stream. OAuth, catalog and quota reads do not consume generation attempts. Transport backoff releases composite permits, sleeps cancellably at or above provider retry hints, then reacquires. Output delivery permanently forbids replay of that request.

Native Codex, Antigravity, Claude and GitHub/Copilot credential refreshes use fenced ownership. Exact native issuer/client and grant identities share encrypted rotations across processes. The shared app database must use a native SQLite driver and configured field encryption; missing encryption fails before consuming a grant. Cached values contain portable credential fields, not another connection's fingerprint or routing settings. Consumed grants follow encrypted successor records and are never presented again; an excessive chain fails closed for reconciliation. OAuth enrollment without an existing connection can use the exact-grant fence; inference refresh with a connection owns network and persistence together.

Generation slots use `OMNI_COORDINATION_PROCESS_ROLE=generation`: actual boot and lazy periodic registration barriers suppress network probes, quota refresh, credential sweeps, sync jobs, background batch polling and scheduled maintenance. Explicit request work and manual job execution remain separate from periodic registration. A separately managed stable maintenance process uses role `maintenance`, enabled shared coordination and `runFencedTask("maintenance", ...)` across its entire startup and lifetime. Losing ownership disables future periodic admission and aborts inherited outbound work. The launcher must preserve that ownership until shutdown. The source change alone does not provision this process.

`getRuntimeCoordinationCapabilities()` performs a durable admission probe. Background readiness additionally requires a confirmed startup barrier or live maintenance authority and a live durable maintenance lease. Credential readiness requires encrypted native storage and supported active OAuth provider coverage; unknown active grant implementations fail closed. Conversation-state readiness is supplied by its own adapter. Canary promotion must verify all capabilities for both immutable generations and the maintenance owner, not trust environment declarations.

Antigravity credits retain their stream observation epoch, reject older writes atomically and preserve observation age across restart. Fragmented frames up to the bounded 1 MiB metadata limit are parsed without changing forwarded bytes. Without provider timestamps, overlapping observations within the same epoch cannot establish server ordering; observations are advisory rather than authoritative billing data.

These changes are source-only until reviewed and explicitly approved for deployment. Offline tests cover multi-process contention, fairness, expiry, owner fencing, conservative cap disagreement, cancellation, encrypted grant sharing, fragmented credits, retry bounds, transport permit release and periodic suppression. They do not establish a real subscription's sustainable concurrency or eliminate process-paused upstream lease-expiry risks. Native upstreams do not accept OmniRoute fencing tokens; process stop/abort and stream-drain monitoring remain part of safe deployment admission.
