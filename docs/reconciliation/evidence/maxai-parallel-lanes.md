## What is missing for 30 safe production lanes

The gap is not “raise `MAX_WAVE` from 6 to 30.” A production design needs all of the following.

1. **An authoritative limit and terms basis.** Obtain provider documentation or explicit approval for the intended account, endpoint, and workload. The recovered native client tops out at six. Do not use the Google-result constant, a local environment cap, or “unlimited” plan wording as a concurrency contract.
2. **Separate logical lanes from active concurrency.** Supporting 30 logical tasks does not require 30 simultaneous provider calls. Permit up to 30 queued logical lanes only if needed and default any future approved active MaxAI concurrency to 2. Do not claim a fixed provider maximum: later recovery proves seven/twelve aggregate host execution but not per-request wire overlap. Make the live cap account-scoped and policy-controlled.
3. **A real product coordinator.** Final2 is a probe. Add a reviewed internal service/API with admission before work starts, bounded queue count **and bytes**, tenant/account fairness, total request and time budgets, deterministic result order, partial-result policy, idempotency, cancellation, and restart recovery. The audit specifically notes an unbounded default provider queue (`C/MAXAI-SOURCE-REVIEW.md:366-370`).
4. **Durable identity.** Persist an opaque `run_id`, stable `lane_id`, wave/ordinal, parent lane, selected account/connection hash, requested/resolved/returned model, host conversation ID, each provider request conversation/response ID, attempt number, continuation parent, timestamps, terminal state, and error class. Never put credentials or raw prompts in this ledger.
5. **Choose one conversation contract explicitly.** Native MaxAI uses one stable conversation per panel plus message bookkeeping. Final2 is stateless and creates a new provider UUID each request while resending full history. Either implement and test native stable per-lane conversations with idempotent `add_messages`, or retain stateless history and label each UUID as request-scoped. Do not call the current UUID a stable lane conversation.
6. **Account affinity and quotas.** Pin every run to one approved connection/account. Enforce per-account semaphore, queue timeout versus execution timeout, daily/run transaction limits, and stop/circuit-break on auth, paywall, quota, 418, or 429. Honor `Retry-After`. Record which account served each request without exposing the credential. The two-lane summary notes one active connection but does not retain request-to-account binding.
7. **Pacing that is policy, not evasion.** Use conservative human-approved scheduling, provider terms, and explicit operator gates. Do not use synthetic “human-looking” text or residential routing to bypass provider controls. The historical record reports a temporary account freeze after rapid automation plus image work (`H/MAXAI-TOOL-API-MAP.md:104-117`); causality is report-level, but the operational risk is real. Final2 pauses follow-ups and wave escalation, but the first requests in a wave still burst together.
8. **Reasoning contract.** Define “reasoning” as provider-exposed text only. Port or reimplement the older robust multi-tag streaming state machine; test tags split at every boundary, attributes/case, multiple and unterminated blocks, native `reasoning_content`, answer-before/after-tag, missing reasoning, byte caps, and cross-lane/out-of-order isolation. Persist raw reasoning only under an explicit privacy policy; hashes/presence should remain the default evidence.
9. **Continuation contract.** Test same-lane history, reply-all, single-lane reply, branching, repeat/idempotency, restart/resume, partial lane failures, timeouts, cancellations, and duplicate tool-result suppression. Add live proof that the selected lane receives only its own prior answer/tool results and document whether provider conversation state is reused.
10. **Tool security and isolation.** Keep per-lane directories and permission scopes. Before exposing general tools, fix the broader prompted-tool fail-open: exact nonce required, exact requested-tool membership, call-count/argument bounds, and rejected-tag handling (`C/MAXAI-SOURCE-REVIEW.md:247-253`). Test malicious cross-lane references, duplicate call IDs, symlink/hardlink/FIFO races, cancellation during tools, and non-idempotent retry behavior.
11. **Memory and retention controls.** Thirty large lanes can multiply decoded input, tokenizer/PDF workers, uploads, and remote retention. Final2's CPU queue is only one active plus eight queued and lacks byte weights, tenant fairness, resource limits, and robust poison recovery (`C/MAXAI-SOURCE-REVIEW.md:354-358`). Overflow uploads the complete conversation with no recovered delete operation. Keep it separately consented and default-OFF.
12. **Immutable current-base release proof.** Reimplement by concern on the current clean upstream anchor; preserve later credential, nonce, routing, cancellation, and queue fixes. Run network-denied tests, stress/load/fault tests, builds, package checks, and rollback/readiness against one immutable candidate. Historical counts from different trees/images cannot be added together.

## Recommended implementation and validation slice

### Slice: tracked two-lane coordinator, scalable in queue but not in active fanout

Build one narrow vertical slice on a disposable current-upstream worktree:

1. Add a default-OFF internal coordinator for **two active MaxAI lanes**. Allow at most 30 logical lane records, but queue them behind an account-scoped semaphore. Set the policy active cap to 2 initially. Keep the implementation configurable, with no claim that six or 30 is the provider maximum.
2. Add a durable metadata ledger with the fields in gap 4. Return stable host `run_id`/`lane_id` values. Extend the executor's internal result metadata to return the fresh provider `conversation_id`/response ID for every request. Do not expose those IDs or raw reasoning in normal logs.
3. Preserve one private history, parser, tool-call ID set, abort controller, working directory, and permission scope per lane. Keep answer and provider-exposed reasoning separate. Keep output ordering independent of completion order.
4. Implement reply-all and selected-lane continuation against the same host lane IDs. In the first slice, keep final2's stateless provider behavior, explicitly name provider IDs `request_conversation_id`, and resend only that lane's history. Defer native server-side history until its add-message idempotency, rollback, and restart semantics are tested.
5. Add account-scoped admission, byte-weighted memory limits, queue and execution deadlines, retry/`Retry-After` policy, total transaction budget, stop-on-safety-status behavior, and cancellation that reaches in-flight provider work. Reject overload before spawning document/tokenizer work.
6. Keep the tool surface to synthetic/local no-side-effect tools until nonce/name authorization is fixed. Keep context spill independently gated and OFF.

Offline acceptance gates:

- Reproduce final2's six-lane reverse-completion barrier.
- Add a **30-logical-lane / active-cap-2** stress test proving at most two upstream mock requests are active, all 30 durable lane records reach one terminal state, memory stays within a declared bound, and queue fairness holds.
